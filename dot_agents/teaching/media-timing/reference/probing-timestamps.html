Probing timestamps

The commands that settle “which frame is really there?” — and the traps that make them lie. Verified on ffmpeg 8.1.

The four questions

QuestionCommand
What does the file claim its start is? ffprobe -v error -select_streams v:0 -show_entries stream=start_time -of csv=p=0 F
…ignoring the edit list? ffprobe -v error -ignore_editlist 1 … (same)
How many frames are really there? ffprobe -v error -count_packets -select_streams v:0 -show_entries stream=nb_read_packets -of csv=p=0 F
What timestamp does each frame carry? ffmpeg -i F -vf "select='lt(n\,5)',showinfo" -f null - 2>&1 | grep pts_time

Reading it: if the first two answers differ, the file has an edit list and you have two clocks. If frame n reports (n+1) × frameDur instead of n × frameDur, the declared lead-in is one frame.

Extracting frames you can look at

# frames 98..101 side by side, in order
ffmpeg -y -i F -vf "select='gte(n\,98)*lt(n\,102)',scale=400:-1,tile=4x1" -frames:v 1 out.png

# where does the picture actually change? (scene cuts, absolute timestamps)
ffmpeg -copyts -ss 55 -i F -t 1.2 -vf "select='gt(scene,0.2)',showinfo" -an -f null - 2>&1 | grep pts_time

Measurement traps

Trap 1 — volumedetect with -ss -af volumedetect combined with an output-side -ss/-t reports across frames outside the window. It gave −29 dB for a window that was actually −91 dB (digital silence). Use atrim and extract the window to a file, then measure that file.
Trap 2 — index vs presentation order select='between(n,…)' counts frames in presentation order, which is what you want — but showinfo’s n resets after a select. Read pts_time, not the printed n, when you need absolute position.
Trap 3 — scene detection lags by a frame select='gt(scene,…)' reports the frame where the difference was measured, which can be one after the true cut. Confirm by extracting the two candidate frames as images.
Trap 4 — probing over HTTP is fine A signed URL works directly: ffprobe "$SIGNED_URL" reads only headers via range requests. No need to download a 1.4 GB source to read its frame rate.

Frame arithmetic

frameDur   = 1 / fps                     # 25fps → 0.040
frameIndex = round(ms × fps / 1000)      # msToFrame — what the pipeline uses
frameTime  = index × frameDur            # a frame is an INSTANT, not a span

on-grid?   = (ms × fps / 1000) is an integer
             51580 × 25/1000 = 1289.5  → off-grid, half-frame boundary

The rule we derived

Output-side -ss keeps the first frame with pts >= ss, then declares the leftover as a lead-in, rounded to a whole frame:

declared_start = round(residual / frameDur) × frameDur
residual       = pts(first kept frame) − ss

Not documented This rule is ours, from 9 measurements on ffmpeg 8.1 at 25/30/23.976 fps. The mov muxer’s edit-list behaviour is not specified in the FFmpeg docs. Cleared by experiment: -avoid_negative_ts 0 changes nothing, and -bf 0 still declares the lead-in — so it is neither negative timestamps nor B-frame delay.

Fixing it

# leaves a one-frame declared lead-in
-ss SEEK -i F -ss OFFSET -frames:v N

# declares 0.000000, same frames, same content
-ss SEEK -i F -vf "trim=start=OFFSET,setpts=PTS-STARTPTS" -frames:v N

setpts=PTS-STARTPTS alone does not work — an output-side -ss shifts timestamps after the filter graph has run.
