Lesson 01 · Media timing

The phantom 40 ms

Why one shot clip carries two clocks, where the extra frame comes from, and how to prove it in four commands. Built from the real fdc1fa99 / dedc4399 bug.

The one idea

A video file answers two different questions, and they can disagree:

  • “Give me frame 100.” — counting. Ignores time entirely.
  • “Give me what’s on screen at 4.028s.” — timestamps. Ignores index entirely.

Our renderer asks the first question (trim=start_frame). The browser asks the second (currentTime). When the file’s timestamps don’t line up with its frame indices, the same clip gives two different answers — and a frame appears in a render that the editor never showed.

Step 1 — Frames are instants on a grid

At 25 fps a frame exists only at exact multiples of 40 ms. Frame N has pts = N × 0.040. There is nothing in between.

Our shot starts at 51.580 — which is not on this grid. It falls between 1289 and 1290.

That is the root of nearly every timing bug in this pipeline: shot boundaries come from a 10 ms dialogue grid, frames live on a 40 ms grid. 51580 × 25 / 1000 = 1289.5 — exactly half-way.

Step 2 — We pick a frame by rounding

msToFrame(51580, 25) = round(1289.5) = 1290. So shot frame 0 is source frame 1290, at 51.600. Bboxes are rebased with the same function, so the whole data model agrees: clip index k = source frame 1290 + k.

Step 3 — We ask ffmpeg for it half a frame early

We could seek to 51.600, the frame’s own timestamp. That’s fragile: ffmpeg keeps frames with pts >= target, so a hair of floating-point either way decides whether frame 1290 survives. So the planner aims at 51.580 — half a frame early, 20 ms of margin on both sides. Frame 1290 is now unambiguously first.

The docs back the first half of this and are silent on the second. “-ss … as an output option: decodes but discards input until the timestamps reach position.” That tells you which frames survive. It says nothing about what timestamp they get — and that silence is the whole lesson.

Step 4 — Where 40 ms is born

ffmpeg now builds the clip’s own timeline starting at zero, and it has a leftover:

you asked for:       51.580
first frame kept:    51.600
leftover gap:         0.020   ← the clip really starts 20 ms later than requested

It records that gap in the file — rounded to a whole frame:

round(0.020 / 0.040) = round(0.5) = 1 frame  →  declares 0.040

Measured, not documented The real gap is 20 ms. The file claims 40 ms. That doubling is the entire bug. The rule declared = round(residual / frameDur) × frameDur was derived from 9 measurements on ffmpeg 8.1 — it is not in the docs.

The clip now says: “my timeline starts at 0, my first frame appears 0.040 in.” So frame index k is presented at (k+1) × 0.040.

And because the planner always aims exactly half a frame early, the residual is always exactly half a frame — always sitting on the rounding boundary, always rounding up. Every clip, every frame rate:

Step 5 — Two clocks, one file

The take ends at 55608 ms. Shot-relative: 55608 − 51580 = 4.028s.

readerhow it selectslands on
browserframe with presentation time ≤ 4.028 → pts 4.00 → index 99source 1389 — the woman
renderertrim=start_frame, indices 79..100 → index 100source 1390 — the man

Why 20-vs-40 flips a frame: the editor assumes clip t=0 ↔ 51.580. With a declared 40 ms lead-in the browser believes frame 0 sits at 51.620, but it really sits at 51.600 — so every frame is reported 20 ms late. Twenty milliseconds is half a frame, so a timestamp near a boundary tips backwards.

Which one is right? The source frame covering 55.608 is 1390 — the man. The renderer matches the source. The browser was faithfully rendering an inaccurate claim.

Prove it yourself

Four commands, on any clip. Full versions in the reference sheet.

# 1. what does the file claim its start is?
ffprobe -v error -select_streams v:0 -show_entries stream=start_time -of csv=p=0 clip.mp4

# 2. same question, ignoring the edit list — if these differ, you have two clocks
ffprobe -v error -ignore_editlist 1 -select_streams v:0 -show_entries stream=start_time -of csv=p=0 clip.mp4

# 3. what timestamp does each frame actually carry?
ffmpeg -i clip.mp4 -vf "select='lt(n\,3)',showinfo" -f null - 2>&1 | grep pts_time

# 4. index vs time: is frame n at n×frameDur, or (n+1)×frameDur?

What this unlocks

You can now answer the question that decides the fix: is the file wrong, or is the reader wrong? Here the file was wrong — which is why compensating in the editor was the wrong instinct (it would break shot durations), and why correcting the clip was right.

Still unverified Three things this lesson does not prove, and you should push on next time: (1) the rounding rule comes from measurement, not from libavformat/movenc.c; (2) the raw start time (0.08–0.12 s, visible with -ignore_editlist) is a separate encoder-delay offset that is only partly characterised; (3) at fractional rates the “exactly half a frame” residual isn’t an exact tie, so the rounding is less certain than at 25 fps.
